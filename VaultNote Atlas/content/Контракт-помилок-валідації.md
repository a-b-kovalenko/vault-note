## 📝 TL;DR

Клієнту потрібен стабільний контракт помилки, а не необроблений текст
винятку Spring. У registration API відповідь містить загальний `code`,
`message` і список `violations`, де кожне порушення має поле, стабільний код і
людське повідомлення.

---

## Формат відповіді

Для невалідного registration request API повертає `400 Bad Request`:

```json
{
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "violations": [
    {
      "field": "email",
      "code": "INVALID_FORMAT",
      "message": "must be a well-formed email address"
    }
  ]
}
```

Клієнт може реагувати на `code` і `field`, не покладаючись на текст
повідомлення. Текст можна локалізувати або змінити без зміни програмної
логіки frontend.

## Як помилка проходить через backend

1. DTO отримує стандартні Bean Validation-анотації, наприклад `@NotBlank`,
   `@Email` і `@Size`.
2. Controller використовує `@Valid` для запуску перевірки request-а.
3. Spring викидає `MethodArgumentNotValidException` при порушенні правил.
4. `GlobalExceptionHandler` перетворює помилку на власний API-контракт.
5. Для кожного `FieldError` формується `ValidationViolation`.

Перетворення кодів відбувається на межі API:

| Bean Validation | API code |
| --- | --- |
| `NotBlank` | `REQUIRED` |
| `Email` | `INVALID_FORMAT` |
| `Size` | `INVALID_LENGTH` |
| `PasswordPolicy` | `PASSWORD_POLICY` |

## Чому не повертати exception напряму

Винятки Spring є деталлю реалізації. Якщо віддати їх без адаптації, клієнт
отримає нестабільну структуру, технічні назви класів або повідомлення, які не
призначені для користувача.

Централізований exception handler також гарантує однаковий формат для всіх
контролерів. У міру зростання API цей контракт можна узгодити з єдиним
problem-details форматом, не змінюючи самі DTO-залежності use case.

## Як це тестувати

Тести мають перевіряти HTTP-статус, загальний `code` і стабільні поля
`violations`. Перевірка точного тексту кожного повідомлення менш надійна,
оскільки текст може змінюватися або локалізуватися.
