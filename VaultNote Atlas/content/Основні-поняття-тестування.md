## 📝 TL;DR

Тест перевіряє очікувану поведінку коду в контрольованих умовах. В Angular ми
зараз використовуємо component tests: створюємо `LoginPage`, змінюємо його
form model і перевіряємо як компонент та його DOM реагують на ці зміни. Такі
тести не звертаються до backend і не замінюють інтеграційні та e2e-тести.

## Рівні тестування

### Unit test

Unit test перевіряє одну невелику одиницю логіки ізольовано:

- функцію;
- validator;
- mapper;
- метод класу;
- невеликий service без реальних зовнішніх залежностей.

**Аналогія з Java/Spring:** JUnit-тест методу сервісу з моками залежностей
через Mockito.

Unit test має бути швидким, детермінованим і показувати помилку в конкретній
одиниці логіки.

### Component test

Component test перевіряє Angular-компонент разом із його шаблоном і локальним
lifecycle:

- component class;
- reactive form;
- template bindings;
- DOM-елементи;
- повідомлення про помилки;
- стан кнопок та інших контролів.

Це не повний application test: backend, реальна база і зовнішні HTTP-сервіси
не запускаються.

**Аналогія з Java/Spring:** найближча паралель — тест web-рівня на кшталт
`@WebMvcTest`: перевіряється presentation boundary у контрольованому
оточенні, а не вся система. Аналогія не повна, бо Angular додатково перевіряє
рендеринг у DOM.

У нашому проєкті component tests для login page лежать у
`frontend/src/app/auth/login-page.spec.ts`.

### Integration test

Integration test перевіряє взаємодію кількох реальних частин системи:

- HTTP endpoint;
- application context;
- service;
- repository;
- database;
- міграції.

**Аналогія з Java/Spring:** `@SpringBootTest` із Testcontainers,
RestAssured, DBRider та PostgreSQL. Детальніше —
[Інтеграційні тести Spring Boot](Інтеграційні-тести-Spring-Boot.md).

### End-to-end test

E2E-тест проходить через систему так, як її використовує користувач:

- відкриває реальний browser;
- переходить між сторінками;
- вводить дані у форму;
- викликає frontend і backend;
- перевіряє кінцевий результат.

E2E-тест має найбільшу цінність для критичного user flow, але він повільніший,
складніший і чутливіший до середовища. У поточній Phase 4 ми його ще не
додаємо.

## Angular test environment

### `describe` та `it`

`describe` групує тести компонента або feature, а `it` описує одну конкретну
поведінку.

**Аналогія з JUnit:** `describe` приблизно відповідає test class, а `it` —
методу з `@Test`.

```ts
describe('LoginPage', () => {
  it('should enable submit for valid credentials', () => {
    // test body
  });
});
```

### `beforeEach`

`beforeEach` готує чистий стан перед кожним тестом. Це важливо, щоб результат
одного тесту не залежав від порядку запуску або змін іншого тесту.

**Аналогія з JUnit:** `@BeforeEach`.

### `TestBed`

`TestBed` створює мінімальне Angular test environment і підключає component
та його залежності.

```ts
await TestBed.configureTestingModule({
  imports: [LoginPage],
}).compileComponents();
```

**Аналогія з Spring:** невеликий тестовий `ApplicationContext` або test slice.
Це не обов'язково повний аналог `@SpringBootTest`, бо тест можна обмежити
одним standalone component і його локальними залежностями.

### `ComponentFixture`

`ComponentFixture` — об'єкт, через який тест керує компонентом і його
відрендереним DOM.

```ts
fixture = TestBed.createComponent(LoginPage);
```

Він дає доступ до двох важливих речей:

- `fixture.componentInstance` — екземпляр класу компонента;
- `fixture.nativeElement` — кореневий DOM-елемент компонента.

Прямої Java/Spring-аналогії для `ComponentFixture` немає. Найближче за ідеєю
це тестовий handle, який одночасно дає доступ до object under test і його
presentation result.

### `componentInstance`

`componentInstance` — це сам екземпляр `LoginPage`, тому через нього можна
перевірити form model:

```ts
expect(page.loginForm.invalid).toBe(true);
```

**Аналогія з Java:** екземпляр класу, який тестується в JUnit.

### `detectChanges`

Angular окремо підтримує стан компонента і DOM. Після зміни state тест викликає
`detectChanges()`, щоб Angular повторно застосував bindings і оновив шаблон:

```ts
page.loginForm.setValue({
  email: 'user@example.com',
  password: 'password',
});
fixture.detectChanges();
```

Прямої Spring-аналогії немає: це специфічна для UI операція. За змістом вона
схожа на явний виклик refresh/render після зміни стану view model.

### `nativeElement`

`nativeElement` використовується, коли потрібно перевірити результат у DOM:

```ts
const button = fixture.nativeElement.querySelector(
  '.submit-button',
) as HTMLButtonElement;

expect(button.disabled).toBe(false);
```

Такий тест перевіряє не лише значення у form model, а й те, що користувач
побачить або зможе натиснути на сторінці. Це ближче до перевірки rendered HTTP
response, ніж до тестування чистого Java-класу, але повної аналогії немає.

## Assertions

Assertion — перевірка очікуваного результату. У поточних Angular-тестах
використовується `expect`:

```ts
expect(page.loginForm.valid).toBe(true);
expect(error.textContent).toContain('Email is required.');
```

**Аналогія з Java:** AssertJ `assertThat(...).isEqualTo(...)` або
`isTrue()`.

Важливо перевіряти observable behavior, а не внутрішню реалізацію. Наприклад,
для login page корисніше перевірити, що кнопка disabled і повідомлення видно,
ніж перевіряти внутрішній список Angular validators.

## Arrange, Act, Assert

Більшість тестів зручно будувати у три кроки:

- **Arrange** — підготувати component і початкові дані;
- **Act** — виконати дію: змінити форму, blur-поле або натиснути кнопку;
- **Assert** — перевірити результат у form model або DOM.

**Аналогія з Java:** це той самий AAA-підхід, який використовується в JUnit
та AssertJ.

```ts
// Arrange
page.loginForm.setValue({
  email: 'user@example.com',
  password: 'password',
});

// Act
fixture.detectChanges();

// Assert
expect(page.loginForm.valid).toBe(true);
```

## Mocks, stubs та spies

- **Mock** — заміна залежності, яка дозволяє керувати її поведінкою і
  перевіряти виклики.
- **Stub** — спрощена реалізація, що повертає заздалегідь визначений результат.
- **Spy** — об'єкт або функція, що записує інформацію про виклики.

**Аналогія з Java:** Mockito `@Mock`, `when(...).thenReturn(...)` і
`verify(...)`.

В Angular залежність можна підмінити test provider-ом через `useValue` або
`useClass`, а окрему функцію — через `spyOn`. Це потрібно, коли компонент
почне використовувати `AuthApiService`: тест не повинен викликати реальний
backend.

Зараз `LoginPage` не потребує mock-ів, бо перевіряє лише reactive form і DOM.

## Ізоляція та детермінованість

Хороший тест:

- не залежить від іншого тесту;
- не залежить від порядку запуску;
- не використовує випадкові або поточні дату й час без контролю;
- не звертається до реальної мережі, якщо це не integration/e2e-сценарій;
- має зрозумілу причину падіння.

**Аналогія з Java:** unit-тест не повинен використовувати спільну базу або
реальний зовнішній сервіс; integration-тест натомість отримує ізольований
Testcontainer і підготовлений dataset.

## Що перевіряємо зараз у login page

У `login-page.spec.ts` перевірено:

- порожня форма є невалідною;
- некоректний email відхиляється;
- валідні credentials активують кнопку submit;
- після взаємодії з невалідним полем у DOM з'являється повідомлення про
  помилку.

Тести ще не перевіряють реальний login HTTP flow, JWT, refresh cookie або
backend `401`. Це буде окремий шар тестування після підключення submit до
`AuthApiService`.

## Межа відповідальності frontend і backend

Frontend-валідація покращує UX: користувач одразу бачить помилку і не робить
очевидно некоректний запит. Вона не є security boundary, бо frontend-код можна
обійти.

Backend залишається джерелом істини для:

- валідації API request;
- password policy під час створення або зміни пароля;
- authentication і authorization;
- перевірки ownership.

Тому frontend може повторювати прості правила для зручності, але backend
повинен перевіряти їх самостійно. Пов'язані пояснення — у нотатках
[Паролі: validation та Argon2id](Паролі-validation-та-Argon2id.md) і
[Контракт помилок валідації](Контракт-помилок-валідації.md).

## Як запускаються тести у VaultNote

```bash
cd backend
./gradlew frontendTest
```

Для перевірки production bundle разом із тестами:

```bash
./gradlew frontendTest frontendBuild
```
