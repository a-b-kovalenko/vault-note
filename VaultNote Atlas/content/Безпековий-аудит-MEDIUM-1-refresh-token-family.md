## 📝 TL;DR

**Статус:** `RESOLVED`  
**Рівень:** `MEDIUM`

Коли backend виявляв повторне використання вже відкликаного refresh token, він
намагався відкликати всю token family, а потім повертав `401`. Через rollback
зовнішньої транзакції це відкликання могло не зберегтися в PostgreSQL. Тепер
family revocation виконується в окремій транзакції, яка commit-иться незалежно
від помилки автентифікації.

## У чому була проблема

Refresh tokens ротуються. Наприклад:

```text
R0 → R1
```

Після нормального refresh `R0` відкликаний, а `R1` активний. Якщо хтось повторно
надсилає `R0`, це ознака reuse — можливої крадіжки токена. У такому випадку
потрібно відкликати всі активні токени цієї token family.

Стара логіка робила два кроки в одній транзакції:

1. відкликала активні токени family;
2. кидала `RefreshTokenAuthenticationFailedException`.

Оскільки exception був unchecked і виникав усередині `@Transactional`, Spring
відкочував усю транзакцію. Тому `R1` міг залишатися активним.

## Ризик

Якщо атакувальник отримав `R0`, він міг першим використати його й отримати
`R1`. Коли справжній клієнт пізніше використовував `R0`, API повертав `401`,
але `R1` атакувальника залишався чинним.

## Як проблему вирішено

- Додано окремий `RefreshTokenFamilyRevocationService`.
- Його реалізація використовує `Propagation.REQUIRES_NEW`.
- Спочатку окрема транзакція commit-ить відкликання активних токенів family.
- Потім зовнішній flow повертає стандартну authentication error.
- `noRollbackFor` не використовується, щоб випадково не commit-ити інші зміни
  зовнішньої операції.

## Як перевірено

- Unit-тест перевіряє делегування до окремого revocation service.
- PostgreSQL integration test створює `R0`, ротуює його в `R1`, повторно надсилає
  `R0`, перевіряє `401` і читає базу в окремому committed state.
- Після reuse обидва токени family мають `revokedAt`, а повторний refresh із
  `R1` також повертає `401`.

## Головний висновок

Критичне security state не повинно відкочуватися разом із помилкою, яку API
навмисно повертає клієнту. Для таких переходів важливо перевіряти не лише HTTP
status, а й фактичний committed стан бази.
