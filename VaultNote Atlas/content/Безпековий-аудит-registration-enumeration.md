## 📝 TL;DR

**Статус:** `NEEDS DECISION`  
**Тип:** suspected issue

Registration повертає різні результати для існуючого та нового email: для
існуючого — специфічний `409`, для нового — `201`. Це може дозволити перевіряти,
чи зареєстрована конкретна адреса. У звіті проблему позначено як таку, що
потребує рішення threat model.

## Як виникає enumeration

Атакувальник надсилає registration request для адреси та порівнює:

- HTTP status;
- error code;
- текст повідомлення;
- можливі записи в logs або timing.

Якщо відповідь для існуючого email стабільно відрізняється, endpoint стає
перевіркою наявності акаунта.

## Чому це важливо

Факт реєстрації email може бути приватною інформацією. Його можна використати
для targeted phishing, credential stuffing або перевірки списку користувачів.

Password-reset request уже використовує нейтральну поведінку `202 Accepted`,
але registration поки має окремий `409`.

## Що потрібно вирішити

Спочатку потрібно зафіксувати threat model продукту:

- чи вважаємо факт реєстрації email чутливою інформацією;
- чи потрібен клієнту явний `409` для UX;
- чи можемо повернути загальну відповідь, а деталь показати лише після
  додаткової перевірки email.

## Можливий напрям виправлення

Якщо enumeration неприйнятний, registration має повертати нейтральну відповідь
для обох випадків і не включати email у публічний error message. Це потрібно
підтвердити API-контрактом, frontend flow та integration tests.

Також rate limiting для registration зменшить масове зондування, але сам по
собі не прибере різницю між `201` і `409`.
