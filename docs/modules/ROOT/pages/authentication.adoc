= Authentication
:description: Current VaultNote login and token delivery flow

VaultNote supports local email/password authentication and Google OAuth2/OIDC
sign-in. A local user must verify the email address before password login
succeeds. Google sign-in requires a verified provider identity and creates the
same VaultNote refresh session used by password login.

== Current login flow

The login endpoint is `POST /api/v1/auth/login`. Its request body contains the
email and password:

[source,json]
----
{
  "email": "user@example.com",
  "password": "Password1234"
}
----

`LoginServiceImpl` performs the following operations:

. Finds the user with roles through `UserJpaRepository`.
. Rejects an unknown, unverified, or incorrectly authenticated user with the
  same `401 Unauthorized` response.
. Creates a short-lived JWT access token.
. Creates a random refresh token, stores only its hash, and assigns a new token
  family identifier.
. Returns the access token in the response body and passes the raw refresh token
  to `AuthController` for cookie delivery.

The JSON response contains:

[source,json]
----
{
  "access_token": "<jwt>",
  "token_type": "Bearer",
  "expires_in": 900
}
----

The API response also sets the refresh-token cookie. The raw refresh token is
never included in the JSON response.

== Stateless access authentication and refresh state

`SessionCreationPolicy.STATELESS` means that Spring Security does not create a
server-side `HttpSession` as the source of authentication. It does not mean
that the application has no persistent state.

VaultNote uses a hybrid model:

* the access JWT is self-contained and validated on every protected request;
* the `SecurityContext` contains the resulting authentication only for the
  current request;
* Angular keeps the access JWT in memory and does not persist it in browser
  storage;
* the refresh session is stateful: PostgreSQL stores its hash, token family,
  expiry, and revocation state, while the browser stores the raw value in an
  `HttpOnly` cookie.

Therefore `POST /api/v1/auth/login` is state-changing even though it does not
create an `HttpSession`: it creates a refresh-token record and sets a cookie.
`POST /api/v1/auth/refresh` rotates that state, and `POST /api/v1/auth/logout`
revokes it and clears the cookie. CSRF protects these side effects; it is not
dependent on Spring creating an HTTP session.

== Protected user profile

`GET /api/v1/users/me` requires the access token in the `Authorization` header:

[source,http]
----
GET /api/v1/users/me
Authorization: Bearer <jwt>
----

The endpoint validates the JWT signature, issuer, and expiration, then returns
the authenticated user's profile, including the identifier, email, display name,
verification state, and roles. `Profile` in the Bruno collection can be used to
verify the request after copying the access token
from a successful `Login` response into the local environment.

The access JWT exists only in the Angular tab memory. A new tab therefore has
the refresh cookie but no access token. The auth interceptor now refreshes the
access token before the first protected request in that tab and then retries
the request with the new Bearer token. Refresh rotation is serialized across
same-origin tabs with the `vaultnote-auth-refresh` Web Lock. `AuthStateService`
also uses a same-origin `BroadcastChannel` to notify other tabs about logout or
session invalidation. The message contains only an event type; it never carries
an access JWT or refresh token. A receiving tab clears its in-memory session
without echoing the message. The authenticated shell clears the local avatar
state and redirects an already open tab to `/login`; a navigation guard avoids
repeating the redirect for an already-ended session.

== Access token

`AccessTokenGenerator` creates a signed JWT with these claims:

* `sub` — the user identifier;
* `roles` — readable role names such as `USER` and `ADMIN`;
* `iss` — the configured issuer;
* `iat` — the issue time;
* `exp` — the expiration time.

The default access-token lifetime is 15 minutes. The local profile overrides it
to three days for convenient manual development and Bruno testing. The token is
intended to be held in Angular memory rather than in `localStorage` or another
persistent browser store.

== Refresh token

The refresh token is an opaque, URL-safe random value. `SecureTokenGenerator`
returns both the raw value and its SHA-256 hash:

* the raw value is sent in the `HttpOnly` cookie;
* only the hash is persisted in `refresh_tokens`;
* `RefreshTokenEntity` stores the user, expiry, token family, and revocation
  state.

The default and local lifetime is seven days. Cookie construction is isolated in
`RefreshTokenCookieFactory` and uses these defaults:

* cookie name: `vaultnote_refresh_token`;
* path: `/api/v1/auth`;
* `HttpOnly`: enabled;
* `SameSite`: `Lax`;
* `Secure`: disabled for local HTTP development and configurable for other
  environments.

== Refresh flow

The refresh endpoint is `POST /api/v1/auth/refresh`. The browser sends the
`vaultnote_refresh_token` cookie automatically:

[source,http]
----
POST /api/v1/auth/refresh
Cookie: vaultnote_refresh_token=<raw-refresh-token>
----

The endpoint does not require a Bearer access token. It is `permitAll` in
`SecurityConfig` because the refresh cookie is the credential for this request.
The service still rejects a missing, unknown, expired, or revoked token with
`401 Unauthorized` and code `REFRESH_TOKEN_AUTHENTICATION_FAILED`.

On a successful request, `RefreshTokenServiceImpl` performs rotation in one
transaction:

. hashes the raw cookie value and locks the matching database row;
. checks the token expiry and revocation state;
. revokes the current token;
. creates a new token in the same token family;
. returns a new access token and replaces the refresh cookie.

The old token cannot be used again. If a revoked token is reused, all active
tokens in its family are revoked and the client must authenticate again. The
family-wide update is implemented by
`RefreshTokenJpaRepository.revokeActiveByTokenFamilyId(...)`.

== Logout flow

The logout endpoint is `POST /api/v1/auth/logout`. The client may send the
current refresh cookie, but the endpoint is idempotent and also succeeds when
the cookie is missing, unknown, or already revoked:

[source,http]
----
POST /api/v1/auth/logout
Cookie: vaultnote_refresh_token=<raw-refresh-token>
----

When the cookie identifies an active token, `RefreshTokenServiceImpl` revokes
that token. `RefreshTokenCookieFactory` always returns a replacement cookie
with an empty value and `Max-Age=0`, which instructs the client to remove it.
The endpoint returns `204 No Content` and is `permitAll` because the refresh
cookie, rather than a Bearer access token, identifies the session.

Logout does not immediately invalidate an already issued access JWT. The JWT
remains valid until its `exp` timestamp; the refresh session is what prevents
the client from obtaining a new access token.

== CSRF and CORS

The backend is prepared for a browser frontend at `http://localhost:4200` and
does not use `Access-Control-Allow-Origin: *` because refresh credentials are
stored in cookies. `CorsConfiguration` reads the allowed origins from
`app.cors.allowed-origins`, which defaults to `http://localhost:4200` and can be
overridden with `VAULTNOTE_CORS_ALLOWED_ORIGINS`.

The frontend obtains an Angular-compatible CSRF token from `GET /csrf`:

[source,http]
----
GET /csrf
----

The response contains a short-lived signed token in JSON. Angular keeps that
value only in the current tab's memory and sends it in the `X-XSRF-TOKEN`
header. No `XSRF-TOKEN` cookie is created or read. `CsrfConfiguration` uses
`StatelessCsrfTokenRepository`, which validates the token signature and expiry
without a cookie or server-side token storage.

Spring Security protects state-changing requests by default. Registration and
email verification are explicitly excluded while those public flows remain
outside the browser session lifecycle. Login, refresh, and logout therefore
require the CSRF header even though they are `permitAll` with respect to Bearer
authentication.

The browser must also pass the CORS preflight. The configured origin is allowed
with credentials for the refresh cookie, while an unknown origin is rejected.
`CsrfCorsIntegrationTest` covers token issuance, missing-token rejection,
allowed preflight, and unknown-origin rejection.

== Public registration and email verification

The public browser flow is:

. `RegisterPage` validates the display name, email, password policy, and
  password confirmation locally, then calls
  `POST /api/v1/auth/registrations`.
. The backend creates an unverified user, assigns the `USER` role, and sends a
  single-use verification link whose plain-text greeting includes the user's
  display name.
. The link opens `/verify-email?token=<raw-token>`. `VerifyEmailPage` submits
  the token to `POST /api/v1/auth/email-verification`, without putting an
  access or refresh token in the URL.
. The page exposes loading, success, and invalid/expired-link states. A
  successful verification does not create a session; it offers navigation to
  `/login`, where the user can authenticate normally.

== Password recovery

VaultNote treats password recovery as a separate, unauthenticated token flow.
It does not reuse an email-verification token. A successful recovery can,
however, confirm the email of an unverified local account because possession of
the recovery link is sufficient for this local-account onboarding path.

=== Requesting a reset

The request endpoint is:

[source,http]
----
POST /api/v1/auth/password-reset/request
Content-Type: application/json

{
  "email": "user@example.com"
}
----

The endpoint returns `202 Accepted` with no account-specific response. An
unknown email, an unverified account, and an existing eligible local account
must not be distinguishable through the API. This prevents account enumeration.

For an existing local account, `PasswordResetServiceImpl` invalidates older
active reset records, generates a cryptographically random token, stores only
its SHA-256 hash in `password_reset_tokens`, and sends the raw token in a
Mailpit/email link:

[source,text]
----
http://localhost:4200/reset-password?token=<raw-reset-token>
----

The raw token is never logged or persisted by the backend. The email includes
the user's display name and explains that a successful reset also verifies an
unverified local email.

=== Confirming a reset

The confirmation endpoint is:

[source,http]
----
POST /api/v1/auth/password-reset/confirm
Content-Type: application/json

{
  "token": "<raw-reset-token>",
  "new_password": "NewPassword1234"
}
----

The service hashes the presented token, locks the matching row, and accepts it
only when it is not expired, used, or invalidated. In one transaction it:

. hashes and stores the new password with the existing Argon2id
  `PasswordEncoder`;
. sets `users.email_verified` to `true`;
. marks the reset token as used;
. invalidates active email-verification tokens for the user;
. revokes all active refresh sessions for the user.

The controller returns `204 No Content` and clears the presented refresh cookie.
The reset flow does not create a new authentication session; the user must log
in again. Already issued access JWTs remain valid until their normal expiry,
because access authentication is stateless and the reset flow revokes refresh
sessions rather than maintaining a server-side JWT blacklist.

Invalid, expired, used, or invalidated reset tokens return the stable
`PASSWORD_RESET_FAILED` error with the neutral message:

[source,json]
----
{
  "code": "PASSWORD_RESET_FAILED",
  "message": "Password reset link is invalid or has expired."
}
----

The reset request and confirmation are state-changing browser requests and
therefore participate in the existing CSRF contract. They are public with
respect to Bearer authentication, but the Angular client must bootstrap CSRF
and send `X-XSRF-TOKEN`.

The backend service and token persistence baseline are implemented, including
PostgreSQL endpoint and concurrency scenarios. The Angular forgot/reset-password
screens remove the token from the address bar after a successful confirmation.
Provider-only Google accounts are supported: password recovery can be used to
set a local password, while an authenticated set/change-password endpoint
remains deferred.

== OAuth provider identity storage

OAuth2/OIDC will not add a provider type or provider subject directly to the
`users` table. Phase 7 introduced a separate `oauth_identities` table with:

* `user_id` — the local VaultNote user;
* `provider` — a stable string value such as `GOOGLE` or `GITHUB`;
* `provider_subject` — the stable identifier issued by that provider;
* `created_at` — when the external identity was linked.

The database will enforce unique `(provider, provider_subject)` so one external
identity cannot belong to multiple VaultNote users, and unique
`(user_id, provider)` so one user cannot link the same provider twice. The
provider type is therefore stored in `oauth_identities.provider`, not in
`users`.

== Google OAuth2/OIDC sign-in

Google sign-in uses a backend-owned authorization-code flow:

. `GET /oauth2/authorization/google` starts the authorization request.
. Spring Security stores the short-lived state and PKCE correlation data in a
  protected cookie instead of `HttpSession`.
. Google returns the authorization code to
  `GET /login/oauth2/code/google`.
. The backend verifies the provider identity, including the stable Google
  `sub` and `email_verified` claim. Matching a local email does not link
  accounts automatically.
. A new provider-only user is created with the `USER` role,
  `email_verified = true`, and no local password. The provider identity is
  stored separately in `oauth_identities`.
. VaultNote creates its normal refresh session and sends the refresh token in
  the existing `HttpOnly` cookie. Angular then obtains the access JWT through
  the existing refresh endpoint and keeps it in memory.

When Google supplies a `picture` claim, the backend imports it only when the
user has no local avatar. The image is downloaded from an approved HTTPS Google
host, validated, normalized to the local `256x256` JPEG format, and stored
separately from the user row. A missing or invalid provider image does not block
login, and an existing local avatar is never overwritten.

== Angular browser flow

The implemented authenticated frontend flow is:

. `LoginPage` validates the form and calls `POST /api/v1/auth/login` after the
  CSRF bootstrap.
. Angular maps the `snake_case` response, stores the access JWT in
  `AuthStateService`, and navigates to `/me`.
. `MePage` calls `GET /api/v1/users/me`; the bearer interceptor adds the access
  JWT to the request.
. When a protected request receives `401`, the refresh interceptor uses the
  `HttpOnly` cookie to rotate the refresh session, stores the new access JWT in
  memory, and retries the original request.
. `Log out` calls `POST /api/v1/auth/logout`, then clears the in-memory state and
  navigates back to `/login` even if the network call fails.

== Configuration

JWT and refresh-token settings are externalized through environment variables:

* `VAULTNOTE_JWT_SECRET`;
* `VAULTNOTE_JWT_ISSUER`;
* `VAULTNOTE_JWT_ACCESS_TOKEN_TTL`;
* `VAULTNOTE_REFRESH_TOKEN_TTL`;
* `VAULTNOTE_REFRESH_TOKEN_COOKIE_NAME`;
* `VAULTNOTE_REFRESH_TOKEN_COOKIE_PATH`;
* `VAULTNOTE_REFRESH_TOKEN_COOKIE_SECURE`;
* `VAULTNOTE_REFRESH_TOKEN_COOKIE_SAME_SITE`.
* `VAULTNOTE_CORS_ALLOWED_ORIGINS`.

There is no default JWT signing secret. Every runtime must provide a unique
value; the application rejects missing, blank, short, and known development
placeholder values. The `local` profile can load a stable value from the
ignored `backend/src/main/resources/application-local-secrets.yaml` file:

[source,shell]
----
cp backend/src/main/resources/application-local-secrets.yaml.example \
  backend/src/main/resources/application-local-secrets.yaml
openssl rand -base64 32
----

Copy the generated value into the local secrets file. `VAULTNOTE_JWT_SECRET`
remains an environment override for CI, containers, and one-off runs. Deployed
environments must also enable the `Secure` cookie flag.

== Integration coverage

`LoginIntegrationTest` runs against PostgreSQL and covers the current login
boundary with three scenarios:

* a verified user receives the access token and refresh cookie, and only the
  refresh-token hash is persisted;
* an incorrect password returns `401 Unauthorized` without a cookie or database
  session;
* an unverified email returns the same neutral `401 Unauthorized` without a
  cookie or database session.

`RefreshTokenIntegrationTest` covers the successful refresh boundary against
PostgreSQL. It verifies that the old token is revoked, the replacement belongs
to the same family, only the replacement remains active, and the new raw value
is delivered in the cookie.

The same test also verifies logout, refresh-token revocation, cookie clearing,
and idempotent logout without a cookie.

== Remaining authentication work

Login, refresh rotation, reuse detection, current-session logout, CSRF, and
CORS are implemented. The following parts are intentionally still pending:

* rate limiting and authentication audit events.

Swagger/OpenAPI remains the reference for the endpoint contract. This page
documents the security behavior and token lifecycle around that contract.
