= ADR 014: OAuth2/OIDC sign-in
:status: accepted
:date: 2026-08-11

== Context

VaultNote currently authenticates users with email and password, then issues
its own JWT access token and rotating refresh-token cookie. The next
authentication phase should support sign-in through an external OAuth2/OIDC
provider such as Google or GitHub without replacing VaultNote's token model.

The current application is stateless after authentication. The OAuth
authorization handshake therefore needs short-lived state that does not turn
the application session into the source of authentication truth.

== Decision

Implement OAuth2/OIDC sign-in as a backend-owned authorization-code flow:

* use Spring Security OAuth2 Client for provider redirects and callbacks;
* keep the authorization state in a short-lived, protected cookie compatible
  with the stateless security model;
* accept only a verified provider identity and map it to a local `User`;
* assign `USER` by default and require explicit rules for account linking;
* issue VaultNote's existing JWT access token and refresh-token cookie after
  successful provider authentication;
* never place access or refresh tokens in redirect URLs;
* add provider buttons and a callback route to the Angular login flow;
* when Google provides a `picture` claim, import it on the backend into the
  existing normalized avatar storage only when no local avatar exists;
* keep the local redirect URI and add the first demo redirect URI
  `https://vaultnote-505715.web.app/login/oauth2/code/google`;
* route the production callback through Firebase Hosting to Cloud Run and
  redirect the completed flow to the Angular `/oauth/callback` route;
* keep Google client credentials in runtime configuration and Secret Manager,
  not in the repository or the frontend bundle;
* use provider-mocked integration coverage and a local browser verification
  flow.

== Consequences

* Users can authenticate through a supported external identity provider.
* VaultNote keeps one authorization model and one access/refresh-token
  lifecycle for both password and provider sign-in.
* Provider configuration, redirect URIs, verified-email semantics, and account
  linking become deployment concerns.
* Provider profile images are treated as untrusted remote input: the backend
  uses an HTTPS host allowlist, bounded download, image validation, and the
  existing `256x256` JPEG normalization before storing them locally.
* Firebase Hosting provides the public browser origin for the first demo, so
  the OAuth callback and cookie handoff can use the same deployed origin while
  the local localhost callback remains available.
* The backend can be implemented and tested before the complete Angular
  application exists, but the final user experience requires a login button and
  callback route.
* Provider credentials and callback configuration must remain environment
  specific and must not be committed.

== Status

Accepted after the Phase 7 Google OAuth2/OIDC implementation, provider-mocked
integration coverage, Google avatar import, and local browser verification were
completed. The production redirect URI is configured for the first GCP demo;
deployed OAuth verification remains pending.
