= ADR 013: CSRF and CORS for browser authentication
:status: accepted
:date: 2026-08-11

== Context

VaultNote is called by an Angular application. During local development the
Angular dev server and Spring Boot API use different origins. In the first
cloud demo Firebase Hosting serves the Angular application and rewrites the
API paths to Cloud Run, so the normal browser flow uses one public origin.
Direct calls to the Cloud Run URL still need the explicit CORS boundary.

The refresh token is delivered in an `HttpOnly` cookie, so the browser can
attach it automatically to refresh and logout requests. CORS must allow the
trusted frontend to call the API, while CSRF must prevent another site from
driving those cookie-backed operations.

The API also has public registration and email-verification endpoints. They
must remain usable before a browser session exists and therefore need an
explicit boundary in the initial CSRF configuration.

== Decision

Use an explicit, environment-driven CORS allowlist:

* default the allowed origin to `http://localhost:4200` for local
  development;
* configure the exact Firebase Hosting origin in the cloud demo;
* allow credentials because the refresh token is in a cookie;
* allow the API methods and headers required by the Angular client, including
  `Authorization`, `Content-Type`, and `X-XSRF-TOKEN`;
* reject origins outside the allowlist; never combine credentials with `*`.

Use a signed, short-lived stateless CSRF token:

* expose `GET /csrf` as a public endpoint;
* return the token and `X-XSRF-TOKEN` header name as JSON;
* keep the token only in Angular memory for the current browser tab;
* require the same token in the `X-XSRF-TOKEN` request header;
* do not create or read an `XSRF-TOKEN` cookie;
* protect state-changing requests by default, including login, refresh, and
  logout;
* explicitly exclude registration and email verification until those public
  flows receive their own browser CSRF integration.

The term `state-changing` refers to an operation with a side effect, not to
the creation of a Spring HTTP session. In this application login creates a
refresh-token record and cookie, refresh rotates that record, and logout
revokes it and clears the cookie. These operations remain CSRF-protected under
`SessionCreationPolicy.STATELESS`.

Keep the CORS origin in `VAULTNOTE_CORS_ALLOWED_ORIGINS`. The cloud demo uses
the Firebase Hosting origin, `Secure=true` for the refresh cookie, and the
existing `SameSite=Lax` refresh-cookie policy. The same-origin Hosting rewrites
simplify normal browser requests, but they do not replace the explicit CORS
configuration for direct API access.

== Consequences

* A trusted Angular client can perform credentialed cross-origin requests.
* The first cloud demo normally uses same-origin Hosting rewrites, while the
  local IDE flow continues to exercise the explicit cross-origin CORS path.
* A foreign origin cannot use CORS to read VaultNote responses and cannot
  provide a valid signed CSRF header for cookie-backed mutation requests.
* The CSRF header token is not an authentication credential. It is short-lived,
  self-verifying, and kept only in the Angular tab memory.
* Bruno and curl do not implement browser CORS automatically. Manual clients
  must first obtain `/csrf`, copy the JSON token, and send it in
  `X-XSRF-TOKEN` for login, refresh, and logout; no CSRF cookie is required.
* Firebase Hosting rewrite only needs the special `__session` name for cookies
  that must reach Cloud Run, such as OAuth authorization and refresh cookies.
  The stateless CSRF token is sent as a header and does not depend on cookie
  forwarding.
* Rate limiting is defined by ADR 015. Authentication audit events and
  production cookie policy remain separate hardening decisions.

== Status

Accepted and implemented by `CorsConfiguration`, `CsrfConfiguration`,
`StatelessCsrfTokenRepository`, `CsrfController`, `SecurityConfig`, and
`CsrfCorsIntegrationTest`.
